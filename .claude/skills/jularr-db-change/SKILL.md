# Jularr DB change

1. Read `docs/DATABASE_CONVENTIONS.md` and `.agent/upgrade-policy.yaml` (currentEpoch 4, minimumSupportedEpoch 3). PostgreSQL via EF Core/Npgsql is canonical; SQLite is an import source only.
2. Find the module that owns the data (`src/Jularr.Web/Features/<Module>`, EF configuration in `src/Jularr.Web/Data`). Extend it; do not create a second table for the same fact.
3. Model rules: `BIGINT GENERATED BY DEFAULT AS IDENTITY` keys, native PostgreSQL types, PK/FK/UNIQUE/NOT NULL/CHECK as integrity boundaries, **no cascading referential actions for application behavior**, indexes only for real access paths (a composite unique already covers its leading column), multi-step mutations in one transaction, no transaction held across HTTP/download/AI/filesystem work.
4. Create the migration with `dotnet ef migrations add <Name> --project src/Jularr.Web` under `src/Jularr.Web/Data/Migrations` and keep `AppDbContextModelSnapshot.cs` consistent (a test fails with PendingModelChanges otherwise). Never edit an applied migration.
5. New or changed tables must be covered by `Data/SqliteImport/SqliteToPostgresImporter` (or explicitly excluded) so Epoch 3 upgrades lose no data; the importer guard tests tell you.
6. Data migration/backfill is one-time, deterministic, idempotent and validated (counts/ids). Then switch reads, then writes, then delete the old runtime path. No indefinite compatibility branch.
7. For query shapes that matter use explicit, parameterized, set-based access; no N+1; no application-side filtering of whole tables; check `EXPLAIN (ANALYZE, BUFFERS)` for hot paths.
8. Tests run against real PostgreSQL (ephemeral container through the test fixtures). Add constraint and invariant tests (unique default, FK, concurrency/idempotency).
