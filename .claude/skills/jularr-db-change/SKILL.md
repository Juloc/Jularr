# Jularr DB change

## Owner-approved clean-cut target (planning vs execution)

Read `docs/CLEAN_CUT_DATABASE.md` when designing **new** schema/features or preparing the initial greenfield replacement. These binding target rules supersede older migration/backfill/legacy target assumptions: Games is a Work, standard internal IDs are bigint, persisted C# `: byte` enums use seeded PostgreSQL smallint `...Types` FK tables, link tables use `Table1Table2s`, Account/Profile and progress are separate scopes, and central artwork/localization/jobs are reused.

**Before explicit cutover approval:** record design in target specs, do not delete the current migration set, convert running EF mappings, reset data, invent compatibility layers or claim target schema is implemented. Current code changes still obey its actually installed schema and coordination scope. **At approved cutover:** audit all EF + raw SQL tables, replace the full legacy migration set with one initial baseline, update all consumers and EF snapshot atomically, test on fresh PostgreSQL. **After cutover:** ordinary forward migrations are appropriate for genuine new features; the clean cut is not a ban on future migrations.

Extends `jularr-task` (owner first, focused test policy, finish/stop). Read `docs/DATABASE_CONVENTIONS.md` and `.agent/upgrade-policy.yaml` once per relevant session, then inspect only the affected owner and schema; no database-wide audit. PostgreSQL via EF Core/Npgsql is canonical.

1. **Owner**: find the module that owns the data (`src/Jularr.Web/Features/<Module>`, EF configuration and migrations in `src/Jularr.Web/Data`). Extend it; never a second table for the same fact.
2. **Model rules**: `BIGINT GENERATED BY DEFAULT AS IDENTITY` keys, native PostgreSQL types, PK/FK/UNIQUE/NOT NULL/CHECK as integrity boundaries, no cascading referential actions for application behavior, indexes only for real access paths (a composite unique already covers its leading column), multi-step mutations in one transaction, no transaction across HTTP/download/AI/filesystem work.
3. **Migration**: for ordinary **current-runtime** work and **post-clean-cut** new features, `dotnet ef migrations add <Name> --project src/Jularr.Web`; keep `AppDbContextModelSnapshot.cs` consistent (PendingModelChanges test fails otherwise). The separately authorized clean-cut initial baseline is the only exception to the old-chain retention rule. Never silently rewrite an applied migration.
4. **Upgrade epoch**: respect `currentEpoch`/`minimumSupportedEpoch` from `.agent/upgrade-policy.yaml`. Where the currently supported source epoch still requires an import path (e.g. SQLite import), new or changed tables must be covered by it or explicitly excluded; if the policy no longer supports that source, do not add import code for it.
5. **Backfill**: only when a *supported* data-retention/upgrade contract requires it. The owner has explicitly chosen **no old Jularr DB backfill** for the test-only clean-cut reset. Remove the obsolete runtime path in the same coordinated cutover. No indefinite compatibility branch.
6. **Queries**: Follow `docs/DATABASE_CONVENTIONS.md` section `Mandatory SQL statement style`: static multiline SQL, absolutely no SQL string interpolation or concatenation, explicit named typed bound Npgsql parameters, uppercase well-indented statements with one selected column per line, all columns table-qualified when more than one table is involved. Set-based reads/writes only, no N+1 or application-side full-table filtering; use `EXPLAIN (ANALYZE, BUFFERS)` on changed hot paths.
   **DTO parameter helper (target candidate):** Follow the limited `SqlParams.From(data).Add(nameof(data.Property))` design in `docs/DATABASE_CONVENTIONS.md` when it reduces repetition. It only maps explicitly selected DTO properties to named typed Npgsql parameters; never generates SQL, auto-binds all DTO fields, assumes all strings are jsonb/citext or bypasses authorization. Null type mapping uses the property’s declared CLR type; enum-byte values are stored as smallint.
7. **Tests**: focused migration, constraint (unique/FK/check), concurrency/idempotency and importer tests, run on real PostgreSQL (ephemeral container through the test fixtures) under the `jularr-task` test budget. No full-suite run.

8. **Outward lists (mandatory)**: Every list returned to API/Razor/client callers must be paginated **in PostgreSQL**, never materialize-all then UI-page. See `docs/DATABASE_CONVENTIONS.md`: `Page` 1-based default 1, `PageSize` default 25/max 100, internally computed checked `Offset = (Page - 1) * PageSize`, and fixed SQL `ORDER BY ... LIMIT @PageSize OFFSET @Offset` with explicitly bound typed parameters. Always use fully unique ORDER BY (append Id tie-break), including unsorted-by-user lists. Keyset (`WHERE Id > @LastId ORDER BY Id`) only as documented measured sequential-feed exception. Share only `PageRequest`/`PageResult<T>`, no default `COUNT(*)`, no unrestricted list exceptions, no SQL interpolation. Test sorting, limits/overflow, filters, scoping, concurrency and page boundaries.
