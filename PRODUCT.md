## Platform

web

## Users

Jularr is run by one owner/operator for a household and friends. Each person has an account with one or more profiles; progress, ratings, history, reader/player preferences and optional learning state belong to the profile and are never merged across profiles.

- **Owner/admin** sets up the instance, storage, downloader, providers, AI, users and backups, and moderates requests. The admin UI is information-dense but structured and web-first. Admin is never on TV.
- **Household and friends** continue watching, reading and listening, discover and request media, and follow releases. They must not need to understand Sonarr-style internals.
- **Learners** are an optional subset: they study Japanese through the media they already watch and read.

What a user sees follows their effective permissions per media type: Hidden, Browse, Request or Instant. Hidden means no navigation and no API access. A user with only book rights sees a pure book app.

## Product Purpose

One self-hosted application to watch, read, listen to, discover and request media. It replaces the Seerr, Sonarr, Radarr and Readarr workflow with a single canonical identity model (Work, Edition, Version, Asset, File, Track) and a single acquisition pipeline behind one consumer action, "Request". A play intent can acquire only the next required episode, so the experience is instant when the user has the rights.

Success means a household member can find something, request or play it and pick it up again on any device, and the owner can run the whole instance without external managers.

## Positioning

Watching, reading, discovery, requests and acquisition share one identity model. Progress survives a file or release being replaced. Plex, Jellyfin, Sonarr, AniList, Trakt and similar services are integrations and data sources, not the architecture. Japanese learning (clickable synced subtitles, local dictionary, FSRS-6 reviews) is an optional module layered over the player and reader. It is not the product's core. It originated as a Japanese anime companion.

## Operating Context

- Self-hosted, Docker-first, modular monolith with PostgreSQL as the only production database.
- Media stays on the owner's own storage. Original media is read-only and never rewritten.
- Acquisition is Usenet-only by product boundary. There are no torrent clients, indexers or magnet handling. SABnzbd and other external clients are compatibility adapters; a native Usenet core is planned, not decided.
- Targeted at a modest single server (about 4-core x86, 16 GB RAM, CPU-only must be useful). Interactive work outranks background work.
- Clients: web and installable PWA; Android phone (WebView shell with native player); Android TV (native, remote-first, browse-first); iOS and iPadOS through Safari/PWA with an optional native shell only if a concrete capability justifies it. TV shows an explicit profile picker.
- Offline: versioned offline book and novel packages with offline-first progress sync. Games are device-local.

## Capabilities and Constraints

- Media types: Anime, Series, Movie, Manga, Light Novel, Book, Audiobook. Web novels are imported from Narou.
- Games are an isolated optional module outside the media core and the Library, planned but secondary.
- Playback prefers Direct Play, then remux, then transcode. Technical diagnostics do not appear in normal user controls.
- Reading uses one unified reader with a capability model. Unsupported settings are hidden, not disabled.
- Localization: English source catalog with stable semantic keys, other locales generated by AI and reviewed by the owner, per-profile UI language. UI language, content language and learning languages are independent. Errors are semantic codes, never localized prose.
- AI is optional. Page rendering never calls AI. Personal outputs stay personal; library outputs are shared, generated once. Cloud AI is never selected silently.
- Consumer vocabulary: Waiting for approval, Requested, Approved, Looking for media, Getting episode, Preparing, Available, Partially available, Monitoring future releases, Needs attention, Cancelled. Consumers never see Wanted, Searching, Importing, release candidates or downloader phases, and there is no consumer "Add" or "Add to Library".
- Consumer UI stays clean; technical controls live in Admin. Permission-restricted actions disappear from the UI and are enforced on the server too.
- Every screen defines loading, empty, partial, error, forbidden and offline states.
- Undecided: native Usenet downloader vs SABnzbd only; native iOS shell; Cast/AirPlay/DLNA via Jularr Connect; roadmap order across #556, #396, #403, Games and Learning v3.

## Product Principles

1. One identity and one action. A single canonical work model and one "Request" action serve every media type.
2. Permission-derived shell. The app each user sees is derived from what they may do, and nothing is shown disabled.
3. Honest and calm. The UI states real platform limits, uses plain consumer words and has no filler text, decoration for its own sake or half-implemented controls.
4. Optional layers. Learning, AI and Games never block the core watch/read/request path.
5. Own your data. Media is read-only on the owner's storage, PostgreSQL is canonical and external services are replaceable sources.

## Accessibility & Inclusion

From `docs/UX.md` and `player/SPEC.md`: full keyboard operability, visible focus, screen-reader labels, no colour-only state, touch targets of at least 44px, reduced-motion support, accessible derived accent colours, a TV focus model, RTL-ready layout and first-class Light and Dark modes. No formal conformance level has been set (open decision).
