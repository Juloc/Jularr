# Persistence

Jularr uses PostgreSQL as its single canonical database.

## Runtime contract

- The connection string is `ConnectionStrings:Default`, overridable with `ConnectionStrings__Default`.
- Jularr fails startup when the configured PostgreSQL database is unavailable.
- There is no SQLite runtime fallback or built-in SQLite import path.
- The supported persistence epoch is the current PostgreSQL epoch declared in `.agent/upgrade-policy.yaml`.
- Fresh/current installations apply the repository's PostgreSQL EF Core migrations at startup.

## Data-access rules

New and intentionally touched persistence follows these rules:

- normal Jularr-owned resource IDs use PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY` / C# `long`;
- provider IDs remain separate external identity/provenance fields;
- prefer explicit, parameterized PostgreSQL SQL behind the canonical Store/Persistence owner for new data-access paths;
- existing EF Core paths are changed intentionally rather than duplicated with a second persistence architecture;
- filtering, joins, grouping, sorting and pagination belong in PostgreSQL when it is the correct execution engine;
- pure reads do not hide mutations or take write locks;
- multi-step business mutations use explicit transaction boundaries;
- database constraints enforce structural validity while application code owns business workflows;
- queries and collections are bounded and important read paths avoid N+1 access.

The complete repository rules are in [MAINTAINABILITY_CONVENTIONS.md](MAINTAINABILITY_CONVENTIONS.md).

## Schema

Jularr has one `AppDbContext` and one PostgreSQL database. The schema contains both EF-modelled entities and explicit SQL-owned tables used by feature stores. They share the same connection and must not become parallel sources of truth.

The migration set under `src/Jularr.Web/Data/Migrations` defines the current installable schema until it is intentionally replaced by a new squashed baseline.

## Search

Local media search uses PostgreSQL full-text and fuzzy matching where available. Search stays bounded, ranks strong title matches ahead of weaker fuzzy matches and does not require external providers for local-library results.

## Derived statistics

Expensive reusable statistics may be persisted as typed, rebuildable PostgreSQL projections when repeated aggregation from source tables would be wasteful. The canonical domain data remains the source of truth.

## Artwork and generated data

Large media/artwork binaries are not stored in PostgreSQL. PostgreSQL stores identity and metadata; generated derivatives and caches live under `/data` and remain rebuildable.

## Diagnostics

Database diagnostics use PostgreSQL statistics/system views for live evidence and bounded Jularr-owned history tables where trends are needed. Sensitive bind values and credentials are not persisted in diagnostics.

Index maintenance is evidence-driven; Jularr does not use blind scheduled index rebuilds.
