# Persistence, search and artwork cache (PostgreSQL cutover)

Canonical design and decision record for Jularr's persistence, full-text/fuzzy
search and local artwork cache under the PostgreSQL epoch (issue #570).

## Status

Implemented on `feat/570-postgres`: the provider swap to EF Core/Npgsql, the
squashed PostgreSQL baseline (`Data/Migrations/*_Epoch4PostgresBaseline`), the
raw-SQL store porting, the one-time SQLite→PostgreSQL importer
(`Data/SqliteImport/SqliteToPostgresImporter`), the shared full-text/fuzzy search
backend (`Features/Search/MediaSearchService`), the local artwork derivative cache
(`Features/Artwork/BesideMediaArtworkCache`), and the conversion of the test suite
to a real PostgreSQL. The build is warning-free, `dotnet ef migrations
has-pending-model-changes` is clean, and the suite runs against an ephemeral
`postgres:18`. Deployment preparation is Juloc/docker PR #374 (PostgreSQL service,
volume, healthcheck, backup note) — an owner step, together with running the
one-time import against an existing `/data` SQLite database.

## Decision

- PostgreSQL, accessed through EF Core with the Npgsql provider, is the single
  canonical database. No permanent SQLite/PostgreSQL dual-write or fallback
  (agent-control rule 7; issue #570).
- The connection string comes from configuration (`ConnectionStrings:Default`,
  overridable by the `ConnectionStrings__Default` environment variable). No
  credentials in the repository.
- The application must fail clearly and refuse to start when PostgreSQL is
  unavailable; it must not silently fall back to a local file.
- Moving from the SQLite format to PostgreSQL is a new persistence epoch
  (agent-control rule 8). `.agent/upgrade-policy.yaml` is bumped **in the same PR**
  that lands the swap, declaring the new current epoch and the oldest SQLite epoch
  the one-time importer accepts.

## Target conventions for new/touched persistence (#852)

The sections below document both the PostgreSQL cutover and existing legacy/current persistence shape. They do **not** make every historical EF/UUID pattern the target for new work.

For all new persistence and intentionally touched persistence paths:

- normal Jularr-owned relational resource identities use PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY` / C# `long`, including normal API/URL resource identity;
- UUID/opaque identifiers are reserved for concrete security/distributed requirements such as session handles, one-time tokens or independently generated identities;
- provider/external IDs remain separate mapping/provenance fields;
- the preferred Jularr data-access path is explicit parameterized PostgreSQL SQL behind the canonical Store/Persistence owner;
- do not add new EF-heavy persistence when a direct SQL Store is appropriate; migrate existing EF incrementally when the affected area is intentionally touched rather than performing a bulk rewrite;
- pure reads are non-mutating and use normal PostgreSQL MVCC; do not introduce SQL Server-style `NOLOCK` or write locks for ordinary UI/API reads;
- while a legacy EF read remains, use `AsNoTracking()` for pure reads;
- do not stringify new numeric IDs/timestamps/booleans when PostgreSQL has the correct native type;
- database constraints validate structure; backend code owns dependent business actions and transaction sequencing; no hidden workflow through cascades/triggers;
- SQL follows the canonical AE01 formatting convention with explicit readable structure and meaningful aliases rather than opaque single-letter aliases.

The complete project-specific boundary, routing and migration rules are in `docs/MAINTAINABILITY_CONVENTIONS.md`. Existing untouched rows/tables are not rewritten solely for conformity; touched code must not extend obsolete patterns.

## Current shape of the data (what the swap must preserve)

2. **Raw-SQL tables (~40).** Created by migrations but *not* part of the EF model;

## Schema strategy: squashed PostgreSQL baseline (Epoch bump)

Mixing providers on one EF migration set is unsupported: the existing migrations
bake SQLite specifics (`type: "TEXT"`/`"INTEGER"`, `Sqlite:Autoincrement`, and
raw `migrationBuilder.Sql(...)` blocks in 41 of them). Rule 8 already prescribes
the fix when an epoch advances: squash to a clean baseline for fresh installs and
remove pre-cutoff migrations/compatibility code.

Procedure:

1. Swap the provider package (`Microsoft.EntityFrameworkCore.Sqlite` →
   `Npgsql.EntityFrameworkCore.PostgreSQL`) in `src/Jularr.Web/Jularr.Web.csproj`.
2. Delete the Epoch-2/3 migrations and `AppDbContextModelSnapshot.cs`.
3. `dotnet ef migrations add <Epoch4PostgresBaseline>` regenerates the 43
   EF-modelled tables with **native PostgreSQL types** and a fresh snapshot
   (`Guid`→`uuid`, `DateTimeOffset`→`timestamptz`, `bool`→`boolean`, autoincrement
   `long`→`bigint GENERATED BY DEFAULT AS IDENTITY`, `string`→`text`/`varchar(n)`
   from the existing `HasMaxLength`).
4. Append the ~40 raw-SQL tables to the baseline. Their `CreateTable`/`CreateIndex`
   operations are copied from the retired migrations with SQLite `type:` strings
   and `Sqlite:Autoincrement` annotations stripped, so the Npgsql generator emits
   native types. These tables are intentionally not in the EF model, so the
   snapshot and `has-pending-model-changes` stay clean.
5. Model refinements for PostgreSQL:
   - `NovelWork.MetadataGenresJson` and `NovelChapter.ContentJson` move from
     `HasColumnType("TEXT")` to `jsonb` (flexible provider payload / structured
     chapter content — the only acceptable use of JSON per the issue; core
     searchable/filterable fields stay relational).
   - Review high-volume access paths and add the indexes below.

Authoritative reference for the current full schema (all 85 tables, columns and
indexes) is produced with `dotnet ef migrations script` on the pre-swap code.

### Indexes for the known access paths

Confirm/introduce indexes for: media/library listing (`Anime.Key`,

## Raw-SQL store porting (SQLite dialect → PostgreSQL)

The stores are mostly portable — they already use `ON CONFLICT ... DO UPDATE`
upserts (33 sites) and parameterised commands. The SQLite-specific pieces to port:

- **Parameter placeholders:** `$name` → `@name` in both the command text and
  `ParameterName` (Npgsql treats `$n` as positional). Affects ~15 store files.
- **`INSERT OR IGNORE` (10) / `UPDATE OR IGNORE` (1)** →
  `INSERT ... ON CONFLICT DO NOTHING` / an explicit `WHERE`.
- **`COLLATE NOCASE` (2, `MangaRepository`)** → `ORDER BY lower(col)` (or `citext`).
- **`LIKE` (case-insensitive on SQLite)** → `ILIKE` on PostgreSQL to preserve
  behaviour (see search).
- **Column types must match what the store binds/reads.** Several stores bind
  `Guid` as its `"D"` string and `DateTime` as an ISO-8601 (`"O"`) string and read
  them back with `reader.GetString(...)` (e.g. `MediaArtworkAssetStore`). Those
  columns stay `text` so the round-trip is unchanged; columns the store binds as
  `int`/`long`/`bool` become `integer`/`bigint`/`boolean`. Each store is verified
  against a real PostgreSQL — strict typing surfaces any mismatch that SQLite's
  dynamic typing hid.
- `Program.cs`: `UseSqlite` → `UseNpgsql`; drop `PRAGMA journal_mode=WAL`; keep the
  fail-fast on startup DB init.
- `SystemHealthService` and `LegacyDatabaseFileMigration`: replace the
  `Microsoft.Data.Sqlite` types. `LegacyDatabaseFileMigration` (which relocated the
  pre-rename `anilingo.db`) is repurposed only to *locate* a legacy SQLite file for
  the importer; the SQLite-specific `DatabaseMigrationBridge` is retired (its
  Epoch-2 bridging and legacy-learning conversion only served pre-cutoff SQLite
  installs and move into the one-time importer).

## One-time SQLite → PostgreSQL migration

A supported existing installation upgrades once, then never reads SQLite again.

- **Trigger & shape:** a startup importer (and an equivalent admin/CLI action)
  that runs when the target PostgreSQL database is empty and a legacy SQLite file
  is present under `/data`. It opens the SQLite file read-only, applies the new
  baseline to PostgreSQL, then copies every table in FK-dependency order inside one
  transaction, converting SQLite value encodings (Guid/text, ISO-8601 timestamps,
  0/1 booleans) to native PostgreSQL types.
- **Idempotency & safety:** deterministic IDs; re-runnable before completion is
  recorded; identity sequences reset with `setval` after copy; row counts verified
  per table; the legacy file is retained (renamed, not deleted) so the import can be
  repeated. It fails clearly if the SQLite epoch is older than
  `minimumSupportedEpoch`.
- **Upgrade policy:** `.agent/upgrade-policy.yaml` is updated in the same PR — new
  `currentEpoch`, `minimumSupportedEpoch` = the SQLite epoch the importer accepts,
  and a `reason` describing the bridge.
- **Operator docs:** `docs/ADMIN_OPERATIONS.md` gains a "PostgreSQL and one-time
  migration" section and its "SQLite" references are updated when the swap lands
  (not before — docs must reflect the running system).

## Derived statistics / aggregate read projections (#858)

### Product/user statistics are real tables

For Jularr, expensive product/user statistics are persisted in normal typed PostgreSQL tables when repeated source-wide aggregation would be wasteful. Examples include per-profile watched/completed counts, watch/listen/read/play duration totals, daily activity buckets, library/storage aggregate buckets, acquisition/import trends and incident/provider-health aggregates.

These are not merely in-memory caches. They have explicit relational columns, PK/UNIQUE/indexes, update timestamps/projection version and rebuild semantics.

Prefer a small number of coherent statistic families such as:
- per-profile all-time summary;
- per-profile daily activity buckets;
- instance/library/storage aggregate buckets;
- acquisition/import daily aggregates;
- incident/provider-health aggregate buckets.

Do not use one generic EAV/JSON metrics table for unrelated statistics.

Canonical progress/session/history owners drive these projections. UI reads never increment counters directly. Updates must be retry-safe/idempotent and expensive rebuilds must be bounded/coalesced.



Expensive reusable statistics are not recomputed from large source tables on every UI/API read.

When a count/distribution/trend is materially expensive and can tolerate a defined freshness window, use a purpose-built relational statistics projection owned by one service. The projection is derived/rebuildable state, never a competing source of the underlying business truth.

Choose among:

- incremental affected-bucket update when the application already knows the canonical change;
- coalesced durable projection refresh for more expensive aggregation;
- periodic refresh for historical/system trends where bounded staleness is acceptable.

Normal reads should then use one/few indexed bounded projection queries. Projection refresh uses set-based SQL/upsert/batching, is idempotent/rebuildable where practical and obeys the resource limits in #857.

Do not create projection tables for already-cheap indexed counts. A statistics table must remove meaningful repeated work, not merely move a simple query elsewhere.

## Full-text + fuzzy search (PostgreSQL FTS + pg_trgm)

A single shared search backend (`Features/Search`, e.g. `MediaSearchService`) used
by every client and page. Requirements from #570: full-text over titles and
textual metadata; typo tolerance; prefix/partial matching; matching across
aliases/localized/native/romaji/English titles; punctuation/casing tolerance;
ranking with exact/strong matches ahead of weak fuzzy matches; indexed execution;
bounded/keyset pagination.

Design:

- **Indexed text per media row.** Each searchable media type (Anime via
  `AnimeMetadata` PreferredTitle/Romaji/English/Native + `Anime.Title`; Manga via
  `MangaSeries` Title/MetadataTitle/MetadataNativeTitle; Novel/Book via `NovelWork`
  Title/MetadataTitle/MetadataNativeTitle + Author) contributes its titles to a
  search document. Use a generated `tsvector` column
  (`to_tsvector('simple', ...)`, weighted A for primary title, B for
  alternates/author) with a **GIN** index, plus a **GIN `gin_trgm_ops`** index on a
  normalized concatenated-titles text column for `pg_trgm` similarity.
- **Extensions:** `CREATE EXTENSION IF NOT EXISTS pg_trgm;` (and `unaccent` for
  punctuation/diacritic folding) in the baseline.
- **Ranking:** exact/normalized-equality and prefix matches first, then `ts_rank`
  full-text hits, then `similarity()` trigram hits above a threshold; ties broken by
  popularity/recency. `word_similarity`/`%` gives prefix and typo tolerance.
- **Consolidation:** the surfaces that today load everything and filter in memory or
  defer to external providers move onto this backend — Anime library grid
  (`LibraryMediaCardQuery`) and Sonarr-migration filter, Manga/Novel library grids,
  Book library dedup (`BookAddStateQuery`). Existing in-reader `LIKE` searches
  (`NovelCatalogQueries.FilterChapters`, `ReaderCore/ReaderTextSearch`,
  `NovelAnnotationService`) switch `EF.Functions.Like` → `EF.Functions.ILike` to keep
  case-insensitive behaviour on PostgreSQL.
- **Pagination:** keyset/cursor where ordering permits; always bounded.

### Unified global search (#434, local half)

`MediaSearchService.SearchAsync(MediaSearchRequest)` is the one search over what is on this
server, rendered at `/Search`. It never calls a provider, so it works when every provider is down.

- **Sources.** Anime (`AnimeMetadata`, plus `Anime` rows the metadata match has not reached),
  light novels and books (`NovelWorks`; `SourceProvider = book-epub` is a Book), manga
  (`MangaSeries`), movies, series, audiobooks and franchises. The first three tables are served by
  the GIN indexes above; movies, series, audiobooks, unmatched anime and franchises are small and
  are matched with the same expressions on the fly. **Follow-up (index tuning):** give them the same
  generated `SearchText`/`SearchVector` columns and GIN indexes.
- **Ranking** is unchanged per source: exact title, prefix, full-text, fuzzy. A franchise scores
  by its own title, or by the title of one of its works at 0.95 of that score; at equal score a
  franchise is listed before the works it groups.
- **Canonical grouping.** Candidate records are resolved to their media-core `Work`
  (`WorkSourceLink`) and collapsed: a book and an audiobook the owner merged (or that were bridged
  to one work) are one row that lists both types. A record with no bridge yet is a row of its own;
  titles are never matched across types. Movies, series and audiobooks are bridged when they are
  imported; anime, novels and manga are not bridged by any library service yet, so they stand alone
  until `LegacyWorkBridge` is called for them (grouping then needs no search change).
- **Visibility.** `MediaSearchRequest.VisibleMediaTypes` is the profile's browseable media types
  (`IAppShellService`); a hidden type is not queried at all, so it cannot appear as a row, inside a
  collapsed row, as a franchise member or as a filter value. Audiobooks are gated by the Book type.
- **Media Facts filters** (type, availability/local, monitored, wanted, language, genre, year).
  Type narrows the SQL; the others filter the best 500 candidates whose facts are loaded set-based
  (`MediaSearchFactsLoader`, a fixed number of queries per type, never one per title) using the
  same definitions as `MediaFactsService`: normalised audio/subtitle/text languages, the household
  content language for manga and novels, provider status. Monitored comes from the anime
  `MonitoringStore` (the other kinds' per-kind stores are not populated by any pipeline yet, so
  nothing else is monitored), wanted from wanted anime units or an open acquisition request
  naming the title's provider id. A filter on an unknown fact (no year, no genre, no language) never matches;
  franchises carry no facts and drop out under a fact filter. Genres are only stored for novels and
  books today, so a genre filter can only match those.
- **Remote half (follow-up).** Provider results merge into the same list by resolving their
  provider identity to a canonical work (`WorkQueryService.FindWorkIdByExternalIdentityAsync`) and
  comparing it with `MediaSearchResult.WorkId`, consuming the #595 shelf/provider contract. Until
  then the page links to Discover with the same query.

## Local artwork derivative cache

Goal: thumbnails render for normal library browsing even when the NAS is
asleep/offline and without contacting external image providers on every page load.
Large binaries are never stored in PostgreSQL — the database keeps
metadata/identity/path; files live under `/data`.

Anime already has this shape: `AnimeArtworkCache` serves rebuildable WebP
derivatives from `/data/cache/artwork/anime/...` in front of the canonical
files beside the media. #570 extends the same pattern to the **non-anime** path
without a second write path:

- **Wrap the existing single read path** `BesideMediaArtworkStore.ResolveAsync`
  (and `MediaArtworkAssetStore`), used for Books and, since #581, Light Novel and
  Manga series covers (`ReadingCoverArtwork`, served by `/Novels/Cover/{id}` and
  `/Manga/Cover/{id}` through this cache).
  The store's own docstring names this the intended #570 integration point.
- **Derivatives** (compact poster/cover thumbnails, e.g. WebP ≤512px) are generated
  from the canonical beside-media file and persisted under
  `/data/cache/artwork/...`, keyed deterministically by media identity + source
  identity + a derivative-version tag, so duplicate provider URLs/identities don't
  create uncontrolled duplicates.
- **Offline resilience:** once a derivative exists it is served from `/data` even if
  the NAS path or external API is unavailable. Generation/download happens in
  background work, not in latency-sensitive page requests.
- **Invalidation & retention:** if the source's size/last-write changes (the
  ownership check `MediaArtworkAssets` already records), the derivative is
  regenerated rather than accumulating stale copies; orphaned derivatives (owner or
  source gone) are cleaned by a periodic sweep. Missing/corrupt artwork degrades to a
  local placeholder without blocking rendering.

## Performance / query tests

Focused tests on a representative large dataset (thousands of series/works,
episodes/chapters, per-profile progress): assert search uses indexed plans (no
sequential scan / no application-side full-table filtering), keyset pagination is
bounded, common library/continue queries avoid N+1 and do not materialize whole
libraries, and fuzzy search returns expected media for common typos with exact
titles ranked first.

## Test-suite conversion

The suite is ~1743 test methods across ~117 files, each building a throwaway
SQLite file (`UseSqlite("Data Source=...;Foreign Keys=True")`) and applying real
migrations through `DatabaseMigrationBridge`; no shared harness, no containers.
Conversion plan:

- A shared test database helper creates an isolated PostgreSQL database per test
  (or per fixture), applies the baseline, and drops it on dispose; the ~117 inline
  construction sites route through it. `SqliteConnection.ClearAllPools()` teardowns
  and SQLite-only connection-string options are removed.
- Tests that pin specific migration IDs via `IMigrator.MigrateAsync("<id>")` target
  the squashed baseline (or the importer), since the pre-cutoff IDs are retired.
- The two in-process harnesses (`ManageSheetPageTestHost`, `LibraryScanTestHost`) and
  the two `EnsureCreated` outliers are aligned with the shared helper.
- CI/local runs use an **ephemeral** PostgreSQL in Docker (e.g.
  `postgres:18` on a throwaway port), separate from any shared/app database, torn
  down after the run.
- **Isolation contract:** each test process derives a unique run id and uses its own
  template (`jt_<unix>_<rand>_tpl`) and databases (`jt_<unix>_<rand>_<n>`), so concurrent
  `dotnet test` runs can share one server (`JULARR_TEST_DB` overrides the default
  `localhost:5433`). A run drops only its own databases at exit; leftovers of crashed runs
  are reclaimed by a later run once older than 12 hours.

## PostgreSQL engine diagnostics history (#859)

Admin database diagnostics use PostgreSQL live statistics/system views for current evidence and Jularr-owned typed history tables for bounded trends.

Relevant live sources include `pg_stat_statements` when configured, `pg_stat_database`, `pg_stat_activity`, `pg_locks`, `pg_stat_user_tables`, `pg_stat_user_indexes`, `pg_stat_io` and version-appropriate vacuum/checkpoint/WAL views.

Because runtime statistics can reset/restart and current locks/activity are ephemeral, Jularr persists sampled **deltas** with a statistics-reset epoch/watermark. Never subtract cumulative counters across a PostgreSQL reset.

Statement history is keyed by PostgreSQL query identity/query id plus time bucket and records only bounded normalized/sanitized query text. Bind values/secrets are never persisted for this feature.

Retention is explicit:
- fine-grained recent samples;
- rolled-up older buckets where useful;
- expiry so observability tables cannot grow indefinitely.

This diagnostics history is operational observability and is separate from #858 product/user statistics. Both use normal typed relational tables and bounded background refresh rather than expensive aggregation on every Admin read.

PostgreSQL index maintenance is evidence-driven. Normal diagnostics show size/use/vacuum evidence; optional deeper `pgstattuple`/`pgstatindex` inspection is on-demand only. Do not implement a SQL Server-style blind fragmentation/rebuild schedule.
