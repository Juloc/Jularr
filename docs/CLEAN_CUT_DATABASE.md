# Jularr database clean cut — binding target architecture

**Status:** Owner-approved **target-state contract**, 2026-10-09. **Not implemented**. The current `dev` schema and runtime remain operational until a separately authorized atomic cutover.

**Scope:** One clean PostgreSQL install baseline for the test-only Jularr deployment, after completing the schema contract. No old-database backfill, permanent compatibility bridges, dual-write, AniLingo/SQLite compatibility or migration chain is required for this cutover. Do **not** delete existing migrations, modify runtime tables, reset an instance, or deploy from this planning document. Once the fresh baseline is installed, subsequent feature changes use ordinary forward-only migrations against the new schema.

This document is the **owner's current product decision** on clean-cut identity, naming, relationships and implementation rules. It supersedes contradictory *target-state* assumptions in `DOMAIN.md`, `ARCHITECTURE.md`, `DOMAIN-AUDIT.md`, `MEDIA_CORE.md`, `IMPLEMENTATION-ROADMAP.md` and old issues. It does not claim those files or today's code have been converted. General database safety and engineering constraints in `DATABASE_CONVENTIONS.md` / central Agent Control remain in force.

## 1. Non-negotiable boundaries

1. **One canonical work:** `Works.Id BIGINT` (C# `long`) for Movie, Series, Book, Manga, LightNovel, Music **and Game**. Anime is a classification of a Movie/Series Work, **not** a competing Work type; audiobook is a format/edition/asset of a Book Work where canonical book identity is shared. Every media-related feature references the same Work identity.
2. **Games decision supersedes the current Games-owned root:** the final schema has no independent `Games.Id`. Keep genuine game-specific platform/release/version/launcher concerns as extension data associated with a Work or WorkVersion.
3. **Account is not Profile:** Account handles sign-in/security/instance roles; Profile owns personal state, locale, restrictions, progress, watchlist, ratings, Learning and service-sync connections. Profile survives reassignment to another Account without changing its ID or copying personal data.
4. **One owner per fact:** no second progress, artwork, media-metadata, acquisition, translation, job, media-session or file pipeline per module. Specialized records may extend common roots but must not duplicate canonical identity or state.
5. **Logical vs physical:** Work > optional Season/Episode or Volume/Chapter/Track > Edition > Version > MediaAsset > StoredFile > MediaTrack/technical analysis. Logical catalog exists without local NAS/files. GamePlatform and game-specific release details are extensions, not identities competing with Work.
6. **Read from database:** UI/list/watchlist/card reads never call NAS or third-party providers. Discovery/acquisition/scan/detection workers update authoritative facts or rebuildable read projections; reads resolve locally with bounded SQL.
7. **No premature execution:** a user-approved target model is not permission to mutate the current schema. Do not mix the clean-cut implementation with concurrent Admin, Arr, Player, or TV feature branches.

## 2. Database naming / type rules

| Item | Required rule | Example |
| --- | --- | --- |
| Table | PascalCase plural, domain name | `Works`, `MediaSegments`, `AccountSessions` |
| Ordinary PK | `Id BIGINT GENERATED BY DEFAULT AS IDENTITY`, C# `long` | `Profiles.Id` |
| Exception PK | Composite keys for simple joins, UUID only for justified public/offline/distributed semantics | `AccountProfiles(AccountId,ProfileId)` |
| Ordinary FK | Singular referenced entity name + `Id`; **always** an explicit FK, never bare `Type`, `Status`, `Provider` when relational | `ProfileId -> Profiles.Id` |
| Enum/type lookup | Persisted fixed enum gets matching plural `...Types` table, except established semantic `MediaTypes`; stable seeded ids, `Key` UNIQUE | `AccountRoleTypes`, `MediaSegmentTypes` |
| Enum FK | Singular name of the **exact type** + `Id` | `AccountRoleTypeId -> AccountRoleTypes.Id`, `GeneratedArtworkStatusTypeId -> GeneratedArtworkStatusTypes.Id` |
| Enum in C# | Explicit values, `enum ... : byte`; persisted as PostgreSQL `smallint` with real FK; PostgreSQL has no native one-byte integer | `enum MediaType : byte` |
| Enum display | `Key` is **stable machine key**, not display name. Translate through shared UI catalog | `Key='poster'` -> localized `Poster` |
| Truly dynamic registry | Real domain table, **not** C# enum or synthetic `...Types` | `Providers`, `GamePlatforms` |
| Link/junction | Singular of first entity + plural of second, with both genuine FKs and usually composite PK | `AccountProfiles`, `FranchiseWorks`, `CollectionWorks` |
| Junction exception | Named relationship with own meaning/state or many differently typed endpoints; document reason | `WorkRelations`, `ImageAssignments` |
| Timestamp | `CreatedAt`, `UpdatedAt`, `FinishedAt`, `timestamptz`, UTC | No mixed `*Utc` suffix |
| Size and timeline | File size `bigint` bytes; seek/position `bigint` milliseconds | `SizeBytes`, `StartMs`, `EndMs` |
| Locale | BCP-47, case-normalized at boundary; real relation uses `UiLocaleId` | `Profiles.UiLocaleId -> UiLocales.Id` |

Never rename a junction to a vague `Members`, `Items` or `Mappings` when its two concrete sides are known. `WorkRelations` is deliberately a typed **directed Work-to-Work edge**; `ImageAssignments` deliberately joins an image to exactly one of several enforced target FKs. Records such as `WorkEpisodes`, `GameReleases` and `PlaybackSessions` are **entities**, not junctions; keep their entity names.

Type tables are deliberately tiny, seeded and code-owned; they are not user-configurable dictionaries. For each persisted enum specify the C# byte values, smallint seed table, explicit FK, no renumbering and a shared localization key. Do not invent a new type table for an enum that never reaches persistence. Do not create generic `EnumValues(TypeName,Value)`.

Use `NOT NULL`, `UNIQUE`, `CHECK` and FK constraints for correctness; application services own business workflows, transactions, authorization and dependent deletes (no cascade-as-business-logic). Index measured `WHERE`/`JOIN`/`ORDER BY` paths, avoid redundant indexes and N+1 queries. Provider identities are unique in their declared provider namespace; never infer canonical identity from title or e-mail similarity alone.

## 3. Canonical target schema by area

Names below are canonical domain ownership, **not an exhaustive ready-to-run DDL inventory**. All fields, unique indexes, constraints, content-target combinations, module-specific tables and EF mappings must be exhaustively signed off before the initial baseline is generated.

### Accounts / Profiles / authentication

| Target table | Core contract |
| --- | --- |
| `Accounts` | `Id bigint`, `Email citext UNIQUE NOT NULL`, `EmailVerifiedAt timestamptz NULL`, **non-unique** `DisplayName`, `AccountRoleTypeId smallint FK`, enabled/timestamps. No `UserName` or `NormalizedUserName` login identity. |
| `AccountRoleTypes` | Built-in `Owner`, `MediaManager`, `User`; instance-level roles, not profile ownership. |
| `Profiles` | `Id bigint`, `OwnerAccountId bigint FK Accounts`, non-unique `DisplayName`, `UiLocaleId bigint FK UiLocales`, selection PIN hash (optional), restrictions/preferences. |
| `AccountProfiles` | Composite PK `(AccountId,ProfileId)`, FKs to `Accounts` and `Profiles`; which Accounts may **select/use** a Profile; **no `CanManage` field**. Profile management by `Profiles.OwnerAccountId` or authorized instance-role action. |
| `AccountPasswords` | Password hash & rotation metadata; per Account, no secret plaintext. |
| `AccountPasskeys` | WebAuthn credential id, public key, flags, counters and metadata; **never private keys**. |
| `AccountTotpFactors` / `AccountRecoveryCodes` | Encrypted TOTP secret and one-way hashed recovery codes; own lifecycles. |
| `AccountExternalLogins` | External provider login identity linked to Account; unique external provider identity. **Distinct from profile-scoped service sync Connections**. |
| `AccountAuthChallenges` | Bounded/expiring verification, reset, enrollment and WebAuthn challenges. |
| `AccountSessions` | Durable Account sign-in/refresh and revocation; current Profile selected in this context; token secret stored hashed. |
| `PlaybackSessions` | Active **or ended** playback, asset/file/device/mode and `EndedAt`; separate domain from AccountSessions. |
| `AccountPermissions` / profile restrictions | Only explicit overrides if supported by effective authorization contracts; avoid parallel role engines. |
| `UiLocales` | `Id bigint PK`, `Locale varchar(...) UNIQUE` plus names/direction/enabled state. |

Account login requires a unique valid e-mail. If an external provider cannot supply a verified usable e-mail, require a verified e-mail enrollment before completing local account creation; do not auto-merge accounts based solely on matching e-mail. An Account may own or access several Profiles; a Profile can be transferred to its own new Account by creating that Account and `AccountProfiles` link, transferring `OwnerAccountId` and optionally unlinking prior access **transactionally**, with explicit authorization. Every personal FK stays on the same `ProfileId`. A Profile PIN is a selection guard, **not** Account auth or 2FA.

Instance module availability is an upper bound, followed by Account role/permissions, profile restriction/capability, and profile module opt-in. UI visibility cannot substitute for server-side permission checks.

| Target | Contract |
| --- | --- |
| `MediaTypes` | Seeded types `Movie`, `Series`, `Book`, `Manga`, `LightNovel`, `Music`, **`Game`**. Anime is a classification of Movie/Series. |
| `Works` | Canonical `Id bigint`, `MediaTypeId smallint FK MediaTypes`, `CanonicalTitle` as a deliberately managed resolved/display projection, dates. |
| `WorkTitles` | Original/localized/alternate/search titles with provenance; authoritative titles are **not duplicated** in separate localized-facts tables. |
| `WorkExternalIdentities` | Correctable provider mappings, namespace and evidence; never an alternative Work ID. |
| `WorkMetadataFacts`, `WorkLocalizedValues`, `WorkFieldProvenance` | Canonical facts, localized **non-title** values, provenance/manual-override protection. |
| `WorkRelations`, `Franchises`, `FranchiseWorks` | Directed prequel/adaptation links are **not** the same as group membership; franchise membership references `WorkId bigint`. |
| `WorkMediaClassifications` | Join of Works to fixed classification types, including Anime; no separate Anime table. |
| `WorkSeasons`, `WorkEpisodes`, `WorkVolumes`, `WorkChapters`, `WorkTracks` | Canonical logical units; their internal IDs use bigint in the new baseline, FK to Work; no legacy episode/chapter id. |
| `WorkEditions`, `WorkVersions`, `MediaAssets`, `StoredFiles`, `MediaTracks`, `MediaTechnicalAnalyses`, `LibraryRoots` | One edition/version/asset/file/inventory chain for all formats. Asset kind as `MediaAssetTypeId` FK; technical stream kind as `MediaTrackTypeId` FK. |
| `EditionExternalIdentities`, edition-scoped `WorkCredits` | Generic ISBN/ASIN/provider identity and audiobook narrators, publishers etc.; no permanent `AudiobookEditionMetadata` duplicate. |
| `GamePlatforms` | Genuine dynamic platform identities. |
| `GameReleases` | **Game-specific extension** with `WorkVersionId bigint PK/FK WorkVersions`, `GamePlatformId bigint FK GamePlatforms`, revision/region/release details. Do not create `Games.Id`. |
| `GameReleaseStoredFiles` | Only where ordered/disc/multi-file release membership is needed: `WorkVersionId -> GameReleases.WorkVersionId` and `StoredFileId -> StoredFiles.Id`, disc/sequence/file-role type. The WorkVersionId is the shared PK/FK of the GameRelease extension; there is no independent GameRelease root. Avoid duplicate `GameReleaseFiles` file identity. |
| `StoredFileHashes` | File-level checksum facts; preserve distinct release-level evidence only if technically necessary and normalized. |

**Game note:** Before writing DDL, ensure all existing GameRelease, platform, hashes, file role and multi-disc semantics have an explicit destination. A specialized extension is valid; duplicating `Games`, `GameTitles`, `GameExternalIdentities` or `GameArtworks` is not. The existing docs' Games-outside-Works statement is **superseded for target-state planning**.

**Audiobook note:** Book + audio edition/asset and narrator credits. Don't create a separate root Audiobook ID if the Work already represents that book. Where a spoken adaptation is genuinely a distinct intellectual work, model the relationship explicitly rather than faking shared identity.

### Images / reader / video timeline / detection

| Target | Contract |
| --- | --- |
| `Images` | One image identity and file/hash/mime/dimensions; binaries live under owned storage, not PostgreSQL. |
| `ImageTypes` | Poster/Cover/Banner/Backdrop/Logo/Chapter/Screenshot/etc.; translated via UI catalog, stable machine `Key`. |
| `ImageAssignments` | `ImageId`, `ImageTypeId`, locale/region/source/priority/manual choice; **exactly one** explicit target FK (`WorkId`, `WorkChapterId`, `MediaChapterId`, etc.); games use **WorkId**, not a GameId. CHECK for exactly-one target. This is an intentional generic relationship table exception. |
| `ImageGenerationRequests` / optional `ImageGenerationPresets` | Generation requests, prompt metadata, profile, operation, accepted Image ID; named presets only if configurable; **no global `ArtworkStyles` enum**. |
| `MediaChapters` | Named chapter/navigation timeline on exact `MediaAssetId`, start/end, chapter ordering, source; distinct from logical written `WorkChapters`. |
| `MediaSegments` | Skip markers on exact `MediaAssetId`: Intro/OP, Recap, Outro/ED, Credits, Preview. **Outro and Credits can overlap**, multiple markers per kind possible; manual corrections outrank imported/provider/detector markers. |
| `MediaSegmentTypes`, `MediaSegmentSourceTypes` | Fixed `...Types` for marker meaning and source. |
| `MediaDetectionRuns` | Detector kind, algorithm version, media/content fingerprint, status, number of matches, timestamps and error, **including successful no-match runs** to prevent infinite reprocessing. |
| `MediaDetectionTypes`, `MediaDetectionStatusTypes` | Seeded fixed detector kind/status types. |
| `ReaderContent`, `ReaderPages`, `ReaderBookmarks`, `ReaderHighlights` | Canonical reading content/navigation annotations. Reader text anchors and edition content identity remain stable for sync. |

Detection uses a **single operation/job queue**, shared cancellation/retry/observability, bounded expensive analysis, no source-file modifications. Existing audio-fingerprint OP/ED is a starting capability; automated recap, scene/video chapter image, ending credits recognition require explicit detection implementations and tests; **do not claim they already work**. A client may offer next-episode/small-player actions based on authoritative resolved ending/credits boundaries and permissions, never a guessed timestamp. Trickplay sprites and fingerprints can remain disposable versioned `/data` caches unless a verified persistence requirement exists; avoid automatic `MediaPreviewAssets` and `ImageVariants` tables solely to describe caches.

### Progress, personal state, collections and UI

| Target | Contract |
| --- | --- |
| `MediaProgress` | Shared identity: `ProfileId bigint FK`, `WorkId bigint FK`, optional canonical target unit FK, `ProgressPositionTypeId smallint FK`, `IsCompleted`, timestamps. One current row per Profile + target. |
| `ProgressPositionTypes` | `Time`, `Reading`, `Game` fixed values. |
| `TimeProgressPositions` | 1:1 `MediaProgressId PK/FK`; `PositionMs`, `DurationMs`. Video/audio/music. |
| `ReadingProgressPositions` | 1:1 `MediaProgressId PK/FK`; `WorkEditionId`, page index, text locator JSONB, per-mille and relevant content/version anchor. Reader/manga/novels. |
| `GameProgressPositions` | 1:1 `MediaProgressId PK/FK`; play time and optional verified/explicit progress %. **Time played is not completion percent**. Savegames/activity sessions are separate if implemented. |
| `MediaPlaybackHistory` | Playback/history events independent of current progress. Reader and gameplay history likewise belong in explicit activity events if their semantics differ. |
| `WatchlistEntries` | Composite `(ProfileId,WorkId)` FK to Profiles/Works. No provider-ID composite masquerading as Work identity. |
| `Collections`, `CollectionWorks`, `ProfileRatings` | Profile ownership; Work-based membership and ratings, no separate Anime/Manga/etc. user lists. |
| `UiTranslationMessages`, `UiTranslations`, `UiLocales` | **One** central catalog for UI/validation/errors; stable machine message key, language fallback exact -> parent -> English, generated/manual/review state. `UiTranslations` links `UiLocaleId -> UiLocales.Id` and `UiTranslationMessageId -> UiTranslationMessages.Id`; `UiTranslationMessages.Key` unique. No `ErrorTranslations` or duplicate Learning/player catalogs. |
| `Operations`, `OperationLogs` | Existing shared background-operation owner reused by acquisitions, import, artwork, detection, media preparation etc. |

`MediaProgress` target semantics must be enforced, not guessed from multiple nullable IDs: use explicit target constraints and per-target unique indexes (including PostgreSQL `NULLS NOT DISTINCT` or partial indexes as appropriate), plus database checks/transactional validation ensuring episode/chapter/track belongs to the row's Work. Enforce **exactly one** matching position extension for each current row and its position type; if SQL cannot enforce the subtype relationship with the chosen shape, finalize an alternative relational constraint design **before** DDL. Preserve cross-device sync idempotency/concurrency and provenance of completed flags (seek alone never establishes viewed/completed).

`WorkAvailabilitySummaries` and `WorkLanguageAvailability`, if expensive aggregation justifies them, are **rebuildable projections**, never a second source of truth. Personal Watchlist/Library/WorkCard queries should use one bounded SQL request resolving access, selected locale/region fallback, `CoverImageId`, `BannerImageId`, available audio/subtitle language arrays, per-unit availability/counts, progress, monitoring/download status and ratings as applicable. Do not call NAS or providers and do not make a query per card. Data sources can change after scan/import/job completion, not as hidden GET side effects.

## 4. What goes away at the cutover

Remove the legacy **tables, readers, writers, duplicate services/tests/config/routes** once the equivalent canonical capability is in place, rather than keeping aliases or forever bridges:

- `Anime`, `Episodes`, `Movies`, `TvSeries`, `NovelWorks`, `MangaSeries`, `Audiobooks`, **`Games` root** and duplicative media-type-specific titles/identity/artworks. Keep specialized GamePlatform/release extension data.
- `GameTitles`, `GameExternalIdentities`, `GameArtworks` -> Work titles/external identities and Images; `GameReleaseFiles` -> unified files plus genuine disc-membership extension.
- `EpisodeProgress`, `NovelProgress`, `MangaProgress`, `AudiobookProgress` as parallel sources; obsolete separate history if equivalent.
- `ProfileWatchlistPreferences` provider-keyed pseudo-watchlist; `FranchiseMembers` -> `FranchiseWorks`.
- `WorkSourceLinks`, migration-only `WorkUnitBindings`, `WorkIdMigrationMap` and other unsupported compat bridges.
- `AccountSessionStates` duplicate session bookkeeping; `OwnerAccounts` -> `Accounts`; `AccountLoginIdentities` -> `AccountExternalLogins`; no generic `AccountCredentials` bag.
- `GameArtworks`, `MediaArtworkAssets`, duplicate `WorkArtwork`/chapter-image inventories -> one `Images`/`ImageAssignments`; `ChapterArtworks` generation lifecycle -> `ImageGenerationRequests`.
- `EpisodeMediaSegments` -> `MediaSegments`; `EpisodeSegmentDetectionStates` -> `MediaDetectionRuns`; generic playback `ActiveSessions` -> `PlaybackSessions`.
- `AudiobookEditionMetadata` -> `WorkEditions`, `EditionExternalIdentities`, edition credits, technical analysis.
- `UiProfileLocales` -> `Profiles.UiLocaleId`, without removing central UI localization catalog.

Do not delete domain-distinct specialized tables merely to reach a low table count: Learning curriculum/cards/reviews, acquisition policy/search/requests, storage reconciliation, game platforms/releases, translations, permissions, file tracks and logs each have valid separate lifecycles.

## 5. Rules for EVERY future feature / agent

Before designing tables or implementing a feature:

1. **Read this target contract** and the relevant module owner, then find existing canonical entities/stores/endpoints. Current user product decisions outrank stale docs. If implementation is still pre-cutover, label schema proposals as **target** and do not quietly convert current runtime assumptions.
2. State the **owning module and source of truth**; distinguish new durable fact, relationship, derived projection, technical cache, transient operation and user preference. Reuse the shared table/pipeline wherever the semantics truly match.
3. Write a **schema contract**: table + columns and PostgreSQL types, PK/FKs (exact table and `Id`), `...Types` enum and seed values, UNIQUE/CHECK/NULL rules, deletion/ownership, source-of-truth and lifecycle. No vague `StatusId`, polymorphic `TargetType/TargetId`, string GUID Work IDs, or JSON blob when relational columns are required.
4. For a junction, use **`Table1Table2s`** by default. Any deviation requires an explicitly stated domain reason. A normal child table is not a junction.
5. Describe **one main read SQL shape** and indexes for watchlist/detail/search/progress etc.; bounded paging/arrays, local joins, no N+1 or synchronous provider/NAS work. Define any projection's invalidation/rebuild strategy.
6. Model auth and profile scope explicitly, enforce server-side authorization + isolation, safe external identity linking, and stable profile ownership during transfers.
7. Describe external/offline/operation failure and idempotency/retry state without inventing another job queue, event store or fallback subsystem.
8. Add stable `UiTranslationMessages` keys for new UI, error and validation texts; use existing translated locale bundles. Never send internal exception details to consumers.
9. Write focused PostgreSQL integrity/integration tests: enum seed/FKs, uniqueness, target combination checks, idempotency/concurrency, per-profile isolation, read-query shape and needed player/reader/arr regressions.
10. If a new feature appears to require changing the canonical root (`Works`, `Accounts`, `Profiles`, `MediaProgress`, `Images`, jobs), provide a concrete contradiction and first review extension options. Do **not** add another competing root as a quick workaround.
11. Coordinate path ownership with other agents; preserve functional slices under active work. Document incompatible target requirements rather than sneak in legacy schema or destructive edits.
12. Review target-contract compliance before merging: exactly one owner, no duplicate table/service, naming and FK rules, constraints, query performance and localization.

Do not solve an incomplete design by speculative extra tables. Conversely, do not force unrelated business lifecycles into generic EAV/polymorphic schemas merely to minimize count.

## 8. Binding PostgreSQL DDL, index and query planning checklist

This is the implementation specification for **how** the target schema must be made safe and performant. It does **not** declare the existing migrations or a complete SQL baseline done. All candidate indexes below are **access-path requirements to validate** against the final queries, not instructions to create every listed index blindly.

### 8.1 Schema completeness before next implementation layer

Before generating migrations, deliver one reviewable target-schema inventory containing **every** EF-mapped and SQL-owned table, all columns with actual PostgreSQL types, nullability, PK/FKs, unique constraints, CHECK constraints, enum seed ids, sensible default values, storage ownership, read/write owner and lifecycle. Maintain a one-to-one disposition (keep/change/delete/new) for all current tables. Prove that all features—Games, learning, acquisition, media metadata, reading, player, subtitle/AI, offline devices, admin, storage reconciliation, localization, requests and operations—still have a canonical data destination. Review the physical schema (including all explicit `migrationBuilder.Sql`/raw SQL stores), not just the EF snapshot.

**Do not move to writing the final baseline with any unresolved cross-table invariants.** The domain design is approved, but its complete physical DDL and query plans are not yet approved or implemented.

### 8.2 Identifiers, FK naming and relational invariants

- Exact FK names: `Accounts.AccountRoleTypeId -> AccountRoleTypes.Id`, `Works.MediaTypeId -> MediaTypes.Id`, `Images` assignment `ImageTypeId -> ImageTypes.Id`. A persisted enum has an explicit `: byte` C# enum, stable numeric seed and PostgreSQL `smallint` lookup with real FK; its code must never be reused for another meaning. No `StatusId`, generic `TypeId`, provider name strings as relational FK, or magic status ints.
- Ordinary internal PK/FK type `bigint`, exception only with a documented technical reason; use composite PK for pure junctions. `Generated By Default As Identity` for generated bigint PK. Public/offline idempotency event IDs may use UUID independently of canonical identity.
- Logical child membership must be consistent. Example: a progress row targeting `WorkEpisodeId` must reference an episode whose `WorkId` equals the row's `WorkId`; if enforceable by composite referenced unique keys and composite FKs, prefer those. Repeat for chapters, editions and tracks. Do not rely only on both separate FKs.
- `ImageAssignments`: exactly one of its supported target FKs is non-null (`CHECK num_nonnulls(...) = 1`); only legal types for each target and manual/locale fallback precedence. Game images target `WorkId` on a Game-classified Work, not a nonexistent `GameId`.
- `MediaChapters` and `MediaSegments`: `CHECK(StartMs >= 0 AND EndMs > StartMs)`, explicit `MediaAssetId`, detector/source provenance. Do not infer a shared timeline between different cuts/assets. Intro, recap, outro, credits, preview may have distinct or overlapping ranges; do not impose an incorrect single-marker-per-kind UNIQUE constraint.
- `MediaProgress`: one row per Profile and exact target with valid `ProgressPositionTypeId`; zero or one concrete child unit (unless a separately modeled Edition/Version target is justified). Enforce uniqueness with a nullable-aware composite unique (`NULLS NOT DISTINCT` on supported PostgreSQL) or equivalent partial unique indexes. Verify matching 1:1 time/reading/game detail; a plain FK from each child does **not** prove every parent has the required child. Final design must close this invariant without speculative triggers or unsupported polymorphic FKs. Completion is an explicit validated action, not inferred from seeking past an end threshold.
- Parent/child names, `FK/UNIQUE/NOT NULL/CHECK` and named indexes must be stable and auditable (`PK_`, `FK_`, `UX_`, `CK_`, `IX_`). Normal business deletes are transactional application operations; no implicit cascade business workflows.
- No unrestricted EAV or generic `TargetType + TargetId` pretending to be a foreign key. If a truly heterogeneous relation is unavoidable, its permitted concrete target FK columns, exclusivity CHECK and owners must be explicit.
- When choosing `numeric`, `double precision`, integer or text, respect semantics: fractional chapter number/ordering must not use a floating-point equality key; ratings/percentages, money/quotas and media timestamps need deliberate exact types/ranges. Large user-facing text and byte content belong in suitable text/storage, not arbitrary `varchar` limits.
- String normalize at the boundary. Required `Accounts.Email` must be case-insensitively unique using the chosen `citext` extension or a defined canonical normalization plus expression/generated-column UNIQUE. Case folding is **not** permission to merge identities from matching provider-reported email. Never use display names as identity keys.

### 8.3 Workload-driven initial index review matrix

| Hot read or write path | Key / candidate PostgreSQL index | Verify |
| --- | --- | --- |
| Account lookup/login | `Accounts.Email UNIQUE` (case-insensitive), `AccountExternalLogins(ProviderId, ExternalAccountId) UNIQUE` | Login does not also scan Username; no extra duplicate email btree |
| Account -> Profile picker | `AccountProfiles PRIMARY KEY(AccountId,ProfileId)`; reverse `(ProfileId,AccountId)` only when profile-to-account reads need it | Enforce access on backend; transfer changes only ownership/link, never ProfileId |
| Auth/session lookup | Unique stored **hash** of session token; candidate `AccountSessions(AccountId,ExpiresAt)` with relevant live/revoked predicate | Expiring/revoking by account/device without table scans |
| Work browsing/library | Candidate `Works(MediaTypeId,CreatedAt DESC,Id DESC)` (or measured real sort), plus actual filtering | Seek/keyset paging, stable tie-break with Id; filters in SQL |
| Search/titles | `WorkTitles` normalized title/search index; GIN trigram for fuzzy `ILIKE` and/or GIN tsvector for FTS if used | Require `pg_trgm`/appropriate extensions in baseline; measure relevance and language/locale |
| Provider identity resolution | `WorkExternalIdentities(ProviderId,ProviderNamespace,ExternalId) UNIQUE`, reverse `(WorkId)` when needed | Namespaces distinguish TMDB TV/movie and other colliding provider ID spaces |
| Season/episode/chapter traversal | Candidate `WorkEpisodes(WorkSeasonId,EpisodeNumber,Id)`, `WorkChapters(WorkId,WorkVolumeId,OrderIndex,Id)` | Define special episode and fractional chapter/order uniqueness before index creation |
| Media inventory | `StoredFiles(LibraryRootId,NormalizedRelativePath) UNIQUE` or an equivalent explicitly defined root-scoped path identity; index targeted `MediaAssets(WorkVersionId)` and reverse target refs | No NAS calls in GET; storage root offline does not remove logical Work |
| Watchlist list/scroll | `WatchlistEntries PRIMARY KEY(ProfileId,WorkId)`, candidate `(ProfileId,AddedAt DESC,WorkId DESC)` for newest-first list | Composite PK already covers Profile lookup; add sorted index only for actual UI sort |
| Progress resume / Continue | Target uniqueness as above and candidate `MediaProgress(ProfileId,LastActivityAt DESC,Id DESC)` | No per-card progress reads, correct completion and offline event ordering |
| Image selection | Candidates on `ImageAssignments(WorkId,ImageTypeId,Locale,Region)` and analogous chapter targets, optionally filtered `WHERE WorkId IS NOT NULL` | Deterministic locale/region/manual override preference and no cross-media image duplication |
| Audio / subtitle languages | Candidate `MediaTracks(StoredFileId,MediaTrackTypeId,Language)` plus efficient Work/asset joins | Bulk aggregate arrays or measured rebuildable projection, no N+1 |
| Video chapters / skip controls | `MediaChapters(MediaAssetId,StartMs,Id)`, `MediaSegments(MediaAssetId,StartMs,Id)` | Efficient ordered timeline; multiple/overlapping segment types supported |
| Detector invalidation | Candidate `MediaDetectionRuns(MediaAssetId,MediaDetectionTypeId,InputFingerprint,DetectorVersion,StartedAt DESC)` | Record successful **no match**; retry/forced rerun history must not be accidentally blocked by UNIQUE |
| Localization bundle | `UiLocales.Locale UNIQUE`, `UiTranslationMessages.Key UNIQUE`, `UiTranslations UNIQUE(UiLocaleId,UiTranslationMessageId)` | Exact -> parent -> English fallback, bundle resolved once/request or cached with invalidation |
| Operation queue | Candidate `Operations(StatusTypeId,NextAttemptAt,PriorityTypeId,CreatedAt,Id)` (adjust fields to actual design) | Atomic work claim using row locks/`SKIP LOCKED` where justified, idempotency and retries |
| History/logging | Targeted `(ProfileId,StartedAt DESC,Id DESC)` or `(OperationId,CreatedAt,Id)` indexes | Retention/archival and realistic cardinality before any partition/BRIN index |

**No default index on every FK or `CreatedAt`**: PostgreSQL automatically indexes PKs and UNIQUE keys, but **not** referencing FKs. Add reverse-FK indexes when join/delete/update or filtering needs them. Do not duplicate indexes already covered by a leading composite key; deliberately select partial and covering `INCLUDE` indexes only with `EXPLAIN` evidence.

### 8.4 Required representative query contracts before baseline

Prove the following SQL shapes as real parameterized, bounded statements, using the same application store/authorization boundary as production:

1. **Watchlist WorkCards:** `ProfileId` security filter; page `WatchlistEntries` first; join `Works`, effective locale/region title and image fallback, Work-level local availability, audio/subtitle languages, completion/progress, wanted/download/monitoring state and rating without one query per Work. Return `WorkId`, `CoverImageId`, `BannerImageId`, `DisplayName`, availability and language arrays. `LEFT JOIN LATERAL`/window selection or bounded pre-aggregation is acceptable; the chosen form must avoid row multiplication from simultaneous artwork/track/episode joins.
2. **Library/discovery/search:** server-side type, profile and visibility filters; deterministic keyset page or bounded offset where appropriate. Use normalized/provider-aware search without local full-table application filtering or synchronous metadata fetch.
3. **Continue/resume:** one profile-scoped read of current progress plus chosen exact locator/time and completed-through episodes/chapters; include game playtime distinctly from completion and avoid false completion on seek.
4. **Playable media selection:** read canonical Work/Edition/Version/Asset/File inventory and known availability; streaming/launch decision may perform authorized I/O only **after** query and playback initiation, never as hidden list GET work.
5. **Administrative queues/jobs:** bounded status/priority/date reads, atomic single-owner work claims, retry/idempotency and no per-row save loops for batch state transitions.

Every hot-path query must have a documented expected cardinality, query inputs, stable ordering, page limit, planned indexes and EXPLAIN (ANALYZE, BUFFERS) output on **representative seeded PostgreSQL data**. Measure both cold and warm cache and pathological joins where relevant; tests should assert result correctness independently of a specific planner choice. Query plans determine final indexes, not guesswork.

### 8.5 Security, concurrency, backups and operational hygiene

- Profile access is verified **before** or inside every profile-scoped data access; authorization derives from authenticated Account, selected Profile, instance policy and effective capabilities. A supplied foreign `ProfileId` or `WorkId` never grants access. Consider database RLS only if its pooled-connection session context and policy coverage can be validated; application authorization remains mandatory.
- Multi-row changes such as Account/Profile ownership transfer, watchlist/profile changes, import attachment, metadata identity correction and progress checkpoint+idempotency acceptance use one database transaction. Apply row locking/optimistic versions for true concurrent write races, not unreliable timestamp comparisons.
- Offline/client-originated retries use durable idempotency keys with uniqueness scoped to their identity and bounded replay/retention; a UUID client event ID may be justified. Server-observed progress must not overwrite a newer client checkpoint accidentally; define revision/conflict semantics per domain.
- Credentials: hash passwords and session/recovery tokens with appropriate password/token-specific algorithms; encrypt TOTP secrets at rest; keep WebAuthn **public** keys but not private keys. Neither the full secret nor exception/stack trace is returned as localized UI errors.
- Every expensive derived summary/cache has one owner, its source table(s), invalidation/rebuild trigger, version and safe cold-start fallback. Favor source-of-truth queries until measured load demonstrates a useful projection. Avoid speculative per-feature caches.
- Database health uses pooled connections, limited transactions, statement timeouts, autovacuum/analyze, bounded large tables, storage checks and observed lock/I/O pressure. No periodic indiscriminate index rebuild, no partitioning before cardinality/retention demands it. Review event/log retention separately from canonical business history.
- The fresh PostgreSQL baseline includes necessary extensions (`citext`, `pg_trgm` **only if used**), every type seed, FK/check/unique and index, permissions/initial instance setup, EF snapshot and raw SQL-owned schema. Validate fresh create/start from an empty instance and `dotnet ef migrations has-pending-model-changes`.
- Before deploying the destructive clean cut, obtain distinct reset authorization and ensure disposable test state and backups/fixtures are accounted for. Future schema extensions create new forward migrations rather than repeating a destructive clean cut.

### 8.6 Gate to next layer

**Next design layer is the application/service contract** (Account/Profile auth, MediaCore/Game, Library/Inventory, Progress/Reader, Artwork/Detection, Acquisition/Operations, localized APIs). It can be planned using this approved model, while the physical SQL/EF baseline is finalized. **Do not start implementation as if the full physical schema were already built**; the exhaustive table/column DDL, FK target consistency and final measured index set are still cutover acceptance gates.

### 8.7 SQL text and parameters — mandatory authoring rule

The owner-approved SQL formatting, fully qualified multi-table column references and **absolute prohibition of SQL string interpolation** are documented with `SqlQueryRaw`, `ExecuteSqlRaw`, named `NpgsqlParameter` examples in [DATABASE_CONVENTIONS.md](DATABASE_CONVENTIONS.md), section "Mandatory SQL statement style". All clean-cut queries, data migrations, APIs, background services and future new features must comply. Never derive SQL syntax or identifier names from request input.
